What is a Config File? (Different from ConfigMap)

There are two types of "config":

#ConfigMap (Kubernetes resource) — What I used in the manifest

apiVersion: v1
kind: ConfigMap
metadata:
  name: voting-config
  namespace: voting-app
data:
  REDIS_HOST: "redis"
  REDIS_PORT: "6379"
  DB_HOST: "db"

Purpose: Store non-sensitive configuration data (env vars, connection strings, settings) Why separate? Can be updated without rebuilding Docker images

# When to Use Separate Config Files?

# Use Separate Files When:
Multiple Environments (dev, staging, prod)
voting-app-dev.yaml → Redis in-memory, small DB voting-app-staging.yaml → Replicas: 2, medium storage voting-app-prod.yaml → Replicas: 5, large storage, HA

# Config Changes Frequently
configmap.yaml (separate) → Update without touching deployments deployment.yaml → Stays stable

# Different Teams
Database team owns db-deployment.yaml
App team owns vote-deployment.yaml
Each can be updated independently

# Large Projects (20+ resources)
Hard to find things in one giant file
Organize by service/component

# Using Kustomize or Helm
Kustomize: Combine base + overlays for different envs
Helm: Template-based, package management

-----------------------------------------------------------------------------------

Order matters:

Namespace first (so resources can reference it)
ConfigMap/Secret (dependency for deployments)
PVC (dependency for stateful services)
Database (needs to exist before other services connect)
Cache (needed by vote and worker)
Applications (vote, result, worker depend on db/redis)

Here's how `kubectl apply` finds your EKS cluster:

---

**Step 1: kubectl reads the kubeconfig file**

When you run:
```bash
kubectl apply -f voting-app-microservices-k8s.yaml
```

kubectl automatically looks for credentials in:
```
~/.kube/config
```

**Step 2: The kubeconfig contains your EKS cluster info**

When you ran `./up.sh annaa`, it executed:

```bash
aws eks update-kubeconfig --name eks-annaa --region eu-central-1
```

This created/updated `~/.kube/config` with: 

```yaml
clusters:
- cluster:
    certificate-authority-data: ...
    server: https://0C66B41B5415F525912DE9B14E0C6E19.gr7.eu-central-1.eks.amazonaws.com
  name: eks-annaa
contexts:
- context:
    cluster: eks-annaa
    user: eks-annaa
  name: eks-annaa
current-context: eks-annaa
users:
- name: eks-annaa
  user:
    exec:
      apiVersion: client.authentication.k8s.io/v1beta1
      command: aws
      args:
      - eks
      - get-token
      - --cluster-name
      - eks-annaa
      - --region
      - eu-central-1
```

---

**Step 3: kubectl connects to your EKS cluster**

When you run `kubectl apply`, it:
1. **Reads `~/.kube/config`** → finds `current-context: eks-annaa`
2. **Gets the cluster server URL** → `https://0C66B41B5415F525912DE9B14E0C6E19.gr7.eu-central-1.eks.amazonaws.com`
3. **Gets authentication** → runs `aws eks get-token` to get temporary AWS credentials
4. **Connects to EKS API server** in AWS → sends your YAML manifest
5. **EKS creates resources** → deployments, services, pods, etc.

---

**Step 4: EKS validates and deploys**

Your `voting-app-microservices-k8s.yaml` is sent to the EKS API server, which:
- Validates the YAML syntax
- Creates the `voting-app` namespace
- Deploys 5 services (vote, result, worker, redis, db)
- Schedules pods on your worker nodes
- Creates LoadBalancer services with external IPs

---

**The flow visualized:**

```
Your machine:
  kubectl apply -f voting-app-microservices-k8s.yaml
         ↓
  Read ~/.kube/config
         ↓
  Get EKS cluster URL & credentials
         ↓
  AWS API Server (in cloud)
         ↓
  Deploy to EKS cluster
         ↓
  Pods running on worker nodes in AWS
```

---

**Verify the connection:**

```bash
kubectl cluster-info
```

Shows the EKS API server URL it's connected to.

```bash
kubectl config current-context
```

Shows you're using `eks-annaa` context.

**The YAML file itself doesn't know about AWS** — it's generic Kubernetes manifests. The magic happens in the `~/.kube/config` file that tells kubectl *where* to deploy.

Storage explanation (quick):

StorageClass (local-sc):

Recipe/template for creating volumes
Says "use local disk storage with immediate binding"
provisioner: kubernetes.io/no-provisioner = Kubernetes doesn't auto-provision; you manually create PersistentVolumes
PersistentVolume (db-pv):

Actual storage pool (10Gi on node disk at /tmp/voting-data)
Claims the storage for the database pod
PersistentVolumeClaim (db-pvc):

Pod's request: "I want 10Gi from local-sc"
Binds to db-pv
Pod mounts it
In your case:

Database uses emptyDir now (temporary, pod-local storage)
Data is lost when pod restarts
Votes from earlier are gone

What is CI/CD?
------------------------------------------------------------------------------------------
CI (Continuous Integration):

Every time you push code to Git, automated tests run
Build Docker images from your code
Run security scans
If all pass → code is "integrated" and ready
CD (Continuous Deployment):

After CI passes, automatically deploy to production
Update Kubernetes with new images
Roll out changes gradually (no downtime)

What triggers the pipeline?

Push to main branch → Full CI/CD pipeline runs
Pull Request → CI only (tests, build, security checks)
Manual trigger → Deploy on-demand
For your voting app, you have 3 services:

Vote (Python Flask):

Tests: pytest or unittest
Build: Multi-stage Docker build
Push: pangpangmarran/voting-app:main-abc1234 (tag with commit hash)
Result (Node.js):

Tests: npm test or mocha
Build: Multi-stage Docker build
Push: pangpangmarran/result-app:main-abc1234
Worker (.NET):

Build: dotnet build
Push: pangpangmarran/worker-app:main-abc1234
Key Components:

1. GitHub Actions Workflow File (.github/workflows/ci-cd.yml)
Defines all steps
Runs on push/PR
Has secrets (Docker Hub credentials, K8s API token)

2. Triggers
push: [main] → Deploy to production
pull_request: [main] → Test only
workflow_dispatch → Manual trigger

3. Jobs
Build Job: Compile, test, build Docker images
Push Job: Push images to Docker Hub
Deploy Job: Update Kubernetes manifests and apply

4. Secrets
DOCKER_USERNAME → for pushing to Docker Hub
DOCKER_PASSWORD → Docker Hub token
KUBE_CONFIG → Kubernetes cluster credentials

GitHub Secrets Location (One place for all):

GitHub repo → Settings → Secrets and variables → Actions

Add all three secrets there:

DOCKER_USERNAME: my username pangpangmarran

DOCKER_PASSWORD: Create a personal access token in Docker Hub and use it here

1. Go to Docker Hub:https://hub.docker.com/settings/security
2. Click "New Access Token"
3. Give it a name (e.g., "GitHub Actions")
4. Select permissions:
Check "Read, Write, Delete"
5. Click "Generate"
6. Copy the token (it only shows once!)
7. Add it to GitHub Secrets:

  Go to your GitHub repo → Settings → Secrets and variables → Actions
    Click "New repository secret"
    Name: DOCKER_PASSWORD
    Value: Paste the token you just copied

KUBE_CONFIG: Encode your Kubernetes config file as base64 and paste it here
Step by step:

cat ~/.kube/config
Copy everything it outputs (the entire YAML content).

Then encode it:

cat ~/.kube/config | base64 -w 0
Copy the entire base64 string (it will be very long, multiple lines).

Add to GitHub:

Name: KUBE_CONFIG
Value: Paste the entire base64 string
GitHub Actions will decode it and use the full config to connect to your cluster.
